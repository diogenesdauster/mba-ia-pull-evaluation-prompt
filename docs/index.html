01

O Desafio

Transformar relatos de bug em user stories ágeis bem estruturadas (formato "Como um... eu quero... para que..." + critérios Dado/Quando/Então). O prompt é avaliado em quinze exemplos via LLM-as-judge.

Input

Bug Report bruto

Texto livre descrevendo o problema. Pode ser uma frase curta ou um relato denso com logs, métricas de impacto e múltiplos problemas correlacionados.

Dashboard mostra contagem errada de usuários ativos. Mostra 50 mas só há 42 na lista.
Output esperado

User Story estruturada

Persona específica, ação clara, benefício de negócio, critérios de aceitação testáveis, e sub-secções proporcionais à complexidade do bug.

Como um administrador visualizando o dashboard, eu quero ver a contagem correta de usuários ativos, para que eu possa tomar decisões baseadas em dados precisos.
Métricas

Cinco métricas, todas ≥ 0.9

Três métricas base (F1, Clarity, Precision) avaliadas via gpt-4o como juiz, mais duas derivadas (Helpfulness, Correctness). Critério: aprovação em todas, não apenas na média.

Dataset

15 exemplos calibrados

Cinco bugs simples, sete médios, três complexos. Cada um com bug report, reference output do gabarito, e metadados de domínio e severidade. Modelo responder: gpt-4o-mini.

02

Quatro Técnicas, Combinadas

Cada técnica resolve uma falha específica do prompt v1 baseline (que pontuava ~0.45-0.50 em todas as métricas). A combinação delas, com atenção ao ordenamento e às sub-secções condicionais, é o que sustenta o salto até ≥ 0.9.

Técnica 01 · Role Prompting

Persona define o vocabulário

Sem persona explícita, o modelo improvisa o ponto de vista. Definir um Product Owner Sênior com 15 anos de experiência ancora tom, vocabulário (negócio, não técnico) e nível de detalhe esperado.

Você é um Product Owner Sênior com 15 anos de experiência em produtos digitais (e-commerce, SaaS B2B, mobile, ERPs e CRMs)…
Técnica 02 · Few-shot Learning

Exemplos comunicam o que prosa não consegue

Nove pares input/output cobrindo a faixa completa de complexidade (3 simples + 5 médios + 1 complexo). Cada exemplo demonstra uma combinação distinta de sub-secções condicionais.

### Exemplo 1 — bug SIMPLE bug_report: Dashboard mostra contagem errada… output: Como um administrador visualizando…
Técnica 03 · Chain of Thought

Raciocínio interno em cinco passos

Antes de gerar output, o modelo executa internamente: classificar complexidade, identificar persona afetada, inferir objetivo de negócio, extrair critérios, selecionar formato. Não verbaliza os passos.

1. CLASSIFICAR COMPLEXIDADE 2. IDENTIFICAR PERSONA AFETADA 3. INFERIR OBJETIVO DE NEGÓCIO 4. EXTRAIR CRITÉRIOS 5. SELECIONAR FORMATO
Técnica 04 · Skeleton of Thought

Três templates por complexidade

SIMPLE: user story + 5 critérios. MEDIUM: + Contexto Técnico e sub-secções opcionais (Severidade, Critérios Adicionais, Critérios de Prevenção, Acessibilidade, Exemplo de Cálculo). COMPLEX: estrutura multi-secção com separadores === ===.

Insight A primeira palavra da resposta DEVE ser "Como" — uma regra trivial mas crítica. Sem ela, o modelo às vezes prefixava metadata ("Complexidade: SIMPLE...") quebrando a estrutura esperada pelo judge. Pequenas regras com efeito grande.
03

Padrões de Dedução por Domínio

O insight central da otimização: as references do dataset incluem padrões standard que um PM sênior infere, mas que o bug original não menciona — backdrop e ESC em modais, audit logs em segurança, email de confirmação em transações. O prompt explicita esses padrões por domínio.

UI / Modais

Backdrop, ESC, foco no modal

Quando bug envolver modal ou overlay, dispara secção Critérios de Acessibilidade com foco do teclado no modal, fechamento via ESC e click no backdrop.

Performance · Mobile

Paginação · RecyclerView · ViewHolder

Listas com mais de 50 itens disparam Critérios Técnicos exigindo paginação (20 por vez), background thread, RecyclerView com ViewHolder pattern e scroll infinito.

Cálculos · Business

Exemplo de Cálculo passo-a-passo

Bug com números + operação matemática (R$, %) dispara secção Exemplo de Cálculo com linha-a-linha (Subtotal, Desconto, Total) usando valores literais do bug.

E-commerce · Estoque

Reserva temporária 15 min

Race conditions em carrinho disparam Critérios de Prevenção: aviso "estoque limitado", reservar estoque por 15 minutos durante checkout.

Integração · Webhooks

Email de confirmação · Audit log

Toda integração via webhook ou gateway implica email de confirmação ao cliente e log de auditoria do evento — mesmo quando o bug não os menciona.

Segurança · OWASP

Severidade · Código OWASP · Dados expostos

Bugs de autorização disparam Contexto de Segurança com Tipo de Falha, Código OWASP (ex: A01:2021), Dados Expostos e Severidade ALTA/CRÍTICA.

Dashboards

Atualizado em tempo real · status filtrado

Métricas em dashboard exigem critério "atualizado em tempo real" e filtro implícito por status apropriado (ex: "apenas usuários ativos").

Multi-persona

Critérios Adicionais para Admins

Quando bug envolve admin + usuário comum, disparar secção Critérios Adicionais para Admins: acesso total, audit log de operações administrativas.

Por que isto funciona O LLM-as-judge premia outputs com vocabulário canônico. Frases como "atualizado em tempo real", "reservar temporariamente 15 minutos", "backdrop", "RecyclerView com ViewHolder pattern" aparecem repetidamente nas references — quando o output contém essas frases exatas, o F1-Score (que mede sobreposição de informação) sobe substancialmente.

Os quatro momentos críticos

As regressões do início

iterações 1 + 2 · −0.020 acumulado

Adicionar imperatividade ao prompt (OBRIGATORIAMENTE, EXATAMENTE 5 critérios, abstrair identificadores) piorou os scores. Lição: imperatividade excessiva quebra a adaptabilidade do modelo a contextos variados.

O debug-by-trace que mudou tudo

iteração 3-5 · primeiro pivot

Em vez de continuar adivinhando, fomos buscar via API do LangSmith as reasonings do gpt-4o judge para cada exemplo. O padrão emergiu: o modelo omitia frases canônicas que as references usavam ("atualizado em tempo real", "backdrop", "RecyclerView", "reservar temporariamente"). Estas frases representavam vocabulário implícito de PM sênior.

A escalada de few-shot

iterações 6-8 · +0.060 em três iterações

Mesmo com vocabulário canônico, o modelo lutava com a estrutura completa das references. A solução foi adicionar references como exemplos few-shot — 3 → 6 → 9 exemplos cobrindo a faixa completa de padrões (validação, dashboards, mobile, e-commerce, modal, cálculo, webhook, security, cross-browser).

Aprovação confirmada em três runs

iter 8 · run 1: 0.9252 · run 2: 0.9494 · run 3: 0.9370

O judge gpt-4o é declarado com temperature=0 mas apresenta variância de ±0.02 entre runs. Verificámos a aprovação em três execuções independentes — em todas as runs, todas as cinco métricas individuais ficaram acima de 0.9.

Recomendação da spec, validada na prática "Use o Tracing do LangSmith como sua principal ferramenta de debug — ele mostra exatamente o que o LLM está pensando." Seguir esta dica foi o ponto de inflexão. Antes disso, estávamos a iterar no escuro.

06

Como Executar

Reproduzir a execução completa, do clone até o resultado final, exige cinco passos. Estimativa de custo OpenAI por avaliação: ~US$ 0,50–1,00.

Pré-requisitos

  • Python 3.9+ (testado em 3.13)
  • Conta LangSmith com API key — handle público definido
  • Conta OpenAI com billing ativo

Setup inicial

# Clone + virtualenv + dependências
git clone https://github.com/diogenesdauster/mba-ia-pull-evaluation-prompt
cd mba-ia-pull-evaluation-prompt
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# Configurar .env (a partir de .env.example)
cp .env.example .env
# Preencher: LANGSMITH_API_KEY, OPENAI_API_KEY, USERNAME_LANGSMITH_HUB,
#            LLM_PROVIDER=openai, LLM_MODEL=gpt-4o-mini, EVAL_MODEL=gpt-4o

Fluxo completo

# 1. Pull do prompt v1 (baseline ruim) do LangSmith Hub
python src/pull_prompts.py

# 2. Validar estrutura do v2 com pytest (6 testes)
pytest tests/test_prompts.py -v

# 3. Push do v2 otimizado (público) para o Hub
python src/push_prompts.py

# 4. Avaliar v2 contra 15 exemplos × 3 evaluators
python src/evaluate.py
